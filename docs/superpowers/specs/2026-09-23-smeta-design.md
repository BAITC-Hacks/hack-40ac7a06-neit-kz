# Спека: смета на мероприятие — комбинации подрядчиков по нескольким позициям

> 23.09.2026. Дополняет `docs/spec.md`. Привязка к коду — коммит `f63b76c`.
> Ссылки даны **именами функций и модулей**, а не номерами строк: репозиторий правится
> параллельно, номера протухают за час.

---

## 0. Три решения, которые определяют всё остальное

| Решение | Следствие |
|---|---|
| **Ядро не трогаем.** `applyFilters`, `match`, `brief` остаются как есть. Позиционный потолок по бюджету (деление общего бюджета по медианам в `parseBrief`) сохраняется | `samples/golden/S1..S12` остаются байт в байт, `PROMPT_VERSION` не меняется, перегенерация эталонов не нужна, живой ключ не нужен. Риск для работающего демо — нулевой |
| **Смета считается из готовых `MatchResponse`, а не новым поиском** | `lib/combo.ts` — чистая функция без сети и без модели. API не меняется ни на байт. Тесты вызывают её напрямую, без HTTP |
| **Позиции независимы → перебора нет** | Эконом = минимум цены в каждой позиции, люкс = максимум. O(n) вместо O(pool^n). Никакого рюкзака, никакой динамики, детерминизм даётся тем же тай-брейком по `id`, что и везде в проекте |

Третье решение — прямое следствие первого. Раз позиционный потолок остаётся, сумма любого набора
из прошедших карточек **арифметически не может** превысить общий бюджет: сумма долей ≤ бюджет,
каждая цена ≤ своей доли. Оптимизировать «самый дорогой в пределах бюджета» нечего — он и так влезает.

**Единственное место, где бюджет реально кусается — проезд.** `estimateTravelCost` не участвует
в позиционном фильтре, поэтому набор с подрядчиком из другого города может вылезти за бюджет.
Это не дефект, это единственный честный случай превышения, и он же самый наглядный.

## 1. Что не так сейчас

`parseBrief` раскладывает «нужны фотограф, ведущий и лайв-бэнд» на три позиции, каждая независимо
проходит `match` и рисует до трёх карточек. Клиент получает три отдельных списка и должен сам
складывать числа в уме. Вопрос, ради которого он вообще пришёл — **«сколько это будет стоить
целиком и влезу ли я в бюджет»** — остаётся без ответа.

Второй пробел виден на реальных данных. Прогон «Алматы · корпоратив · 2026-10-01 · фотограф +
ведущий + лайв-бэнд · бюджет 1 000 000 ₸»:

| Позиция | Доля по медиане | Исход | Самый дешёвый в каталоге |
|---|---|---|---|
| Фотограф | 120 000 ₸ | `NO_ONE_PASSES` | 150 000 ₸ |
| Ведущий | 400 000 ₸ | `NO_ONE_PASSES` | 500 000 ₸ |
| Лайв-бэнд | 460 000 ₸ | `NO_ONE_PASSES` | 800 000 ₸ |

Три пустых экрана подряд. При этом ответ, который клиенту нужен, лежит на поверхности:
**минимальный реальный ценник такого мероприятия — 1 450 000 ₸, бюджет мал в 1,45 раза.**
Сегодня этого не говорит никто, потому что сказать это можно только над всеми позициями сразу.

## 2. Модуль `lib/combo.ts`

```ts
export type ComboKind = 'economy' | 'custom' | 'lux';

export type ComboPick = {
  category: string;
  cardId: string;
  name: string;
  priceFromKzt: number;
  /** проезд из другого города; 0 для местных */
  travelKzt: number;
  /** карточка взята из блока послаблений — в наборе есть оговорка */
  soft?: string;
  /** этот же профиль закрывает и другую позицию */
  alsoCovers?: string;
};

export type Combo = {
  kind: ComboKind;
  label: string;              // «Эконом» | «Ваш выбор» | «Люкс»
  picks: ComboPick[];
  totalKzt: number;           // сумма цен + сумма проезда
  travelKzt: number;
  budgetKzt?: number;
  /** >0 — остаток, <0 — превышение; undefined, если бюджет не назван */
  deltaKzt?: number;
  fitsBudget: boolean;
  /** категории, по которым в набор некого поставить */
  missing: string[];
  /** true — набор собран из `nearestCards`, то есть из тех, кто не прошёл фильтры */
  hypothetical: boolean;
  line: string;
  note: string;
};

export type ComboPosition = {
  category: string;
  cards: Card[];
  softCards: Card[];
  nearestCards: Card[];
};

export function buildCombos(
  positions: ComboPosition[],
  budgetKzt?: number,
  selection?: Record<string, string>,   // category → cardId
): Combo[];
```

Функция чистая: ни `Date.now()`, ни сети, ни модели. Тот же контракт, что у `applyFilters`.

## 3. Правила сборки

### 3.1 Кандидаты

Эконом и люкс берутся **только из `cards`** — тех, кто прошёл все семь фильтров и виден на экране.
Смета не имеет права ссылаться на то, чего человек не видит.

`softCards` доступны **только ручным выбором**. Когда клиент сам ставит в набор карточку
с оговоркой, в сумму входит `relaxation.travel.totalKzt`, в `ComboPick.soft` уезжает
`relaxation.label`, и набор честно несёт эту оговорку в `note`.

### 3.2 Выбор внутри позиции

| Набор | Правило | Тай-брейк |
|---|---|---|
| Эконом | минимальный `priceFromKzt` среди `cards` | меньший `id` лексикографически |
| Люкс | максимальный `priceFromKzt` среди `cards` | меньший `id` лексикографически |
| Ваш выбор | `selection[category]`, иначе первая карточка (она уже отсортирована по `score` в `match`) | — |

Тай-брейк по `id` — то же правило, что в `byScoreThenId` (`lib/scoring.ts`). В данных есть
реальная пара с одинаковой ценой: HK-23752 и HK-31819, оба лайв-бэнда по 1 150 000 ₸.
Без тай-брейка «Люкс» менялся бы между прогонами.

### 3.3 Сумма

```
totalKzt = Σ priceFromKzt + Σ travelKzt
deltaKzt = budgetKzt − totalKzt        // undefined, если бюджет не назван
fitsBudget = deltaKzt === undefined || deltaKzt >= 0
```

Бюджет для сравнения — **общий, исходный**, а не сумма долей. Доли по медианам — внутренняя
механика фильтра, клиенту в смете показывается та сумма, которую он назвал сам.

### 3.4 Совпадающие наборы

На реальных данных (бюджет 3 000 000 ₸, та же тройка) «Ваш выбор» по умолчанию **совпадает
с экономом**: самый подходящий по совпадению оказался и самым дешёвым во всех трёх позициях.

Набор при этом не прячется и не схлопывается. Строка остаётся на месте, в `note` уходит
«совпадает с экономом: самый подходящий оказался и самым дешёвым». Прятать — значит показать
два варианта вместо трёх и заставить судью гадать, куда делся третий.

### 3.5 Неполный набор

По измерению из README три и более подходящих подрядчика находятся только в 7% запросов.
Позиция без единой прошедшей карточки — **норма, а не край**. Набор всё равно собирается
из того, что есть, категория уезжает в `missing`, и строка это называет вслух.

### 3.6 Гипотетический набор

Если `cards` пусты **во всех** позициях, смета собирается из `nearestCards` (они уже считаются
в `match`, когда не проходит никто), помечается `hypothetical: true` и отвечает на тот вопрос
из §1, который сегодня остаётся без ответа: сколько стоит минимально возможный набор и во сколько
раз он выше бюджета. Набор при этом **нельзя выбрать** — он справочный, кнопок выбора у него нет.

### 3.7 Один профиль на двух позициях

`Contractor.categories` — множество, и это не редкость: **13 профилей из 66** числятся больше
чем в одной категории. Пересечения в данных:

| Сколько профилей | Категории |
|---|---|
| 4 | Национальный ансамбль + Танцевальный коллектив + Шоу-программа |
| 4 | Банкетный зал + Загородная площадка + Ресторан |
| 2 | Банкетный зал + Отель + Ресторан |
| 1 | Фото и видеобудки + Шоу-программа |
| 1 + 1 | Банкетный зал + Ресторан; Банкетный зал + Отель |

Значит запрос «нужны национальный ансамбль и шоу-программа» приведёт один и тот же профиль
в обе позиции — например HK-92824 Поньо, Алматы, 500 000 ₸.

Молча подменять его на второго по списку нельзя: это решение за клиента, и оно меняет сумму.
Правильное поведение — оставить как есть, проставить `alsoCovers` обеим позициям и сказать
вслух: «Поньо закрывает обе позиции — дешевле на 500 000 ₸, уточните, потянет ли один состав
две программы за вечер». Цена при этом считается **один раз**, а не дважды.

## 4. Строка

Считается кодом, не моделью — тот же принцип, что у `buildMessage` в `lib/match.ts`:
числа обязаны быть точными, модель к ним не подпускается. Разряды через неразрывный пробел
(`toLocaleString('ru-RU')`), как уже принято в проекте.

Пять форм, все — на реальных данных «Алматы · корпоратив · 2026-10-01»:

**В бюджет** (бюджет 3 000 000 ₸, эконом):
```
Шикамару Нара 150 000 + Куррапика 500 000 + Мегумин 800 000
= 1 450 000 ₸ · остаток 1 550 000 ₸
```

**Люкс** (тот же запрос):
```
Леорио Паради 350 000 + Мицури Канроджи 650 000 + Дзэнъицу Агацума 1 150 000
= 2 150 000 ₸ · остаток 850 000 ₸
```

**С проездом** (ведущий взят из послаблений, `FLY_IN` из Астаны):
```
Шикамару Нара 150 000 + Тэнъя Иида 1 000 000 + проезд 59 600 + Мегумин 800 000
= 2 009 600 ₸ · остаток 990 400 ₸
```

**Неполный**:
```
Шикамару Нара 150 000 + Куррапика 500 000 = 650 000 ₸
· лайв-бэнд не собран: никто не проходит по дате
```

**Гипотетический** (бюджет 1 000 000 ₸, не прошёл никто):
```
Дешевле этого набора в каталоге нет: Шикамару Нара 150 000 + Куррапика 500 000
+ Мегумин 800 000 = 1 450 000 ₸ · это в 1,45 раза выше вашего бюджета
```

Кратность («в 1,45 раза») берётся только при превышении больше чем в 1,2 раза; при меньшем
пишется абсолютная разница. Иначе «в 1,03 раза выше» звучит как отписка вместо числа.

## 5. Интерфейс

Блок над позициями, три строки, выбранная подсвечена:

```
Смета на мероприятие · бюджет 3 000 000 ₸
┌────────────────────────────────────────────────────────────┐
│ ● Эконом      1 450 000 ₸   Шикамару · Куррапика · Мегумин │
│ ○ Ваш выбор   1 450 000 ₸   совпадает с экономом           │
│ ○ Люкс        2 150 000 ₸   Леорио · Мицури · Дзэнъицу     │
└────────────────────────────────────────────────────────────┘
── Фотограф ──────────────────────────────────────────────────
 [карточка] [карточка]
── Ведущий ───────────────────────────────────────────────────
 [карточка] [карточка]
```

- клик по строке «Эконом»/«Люкс» проставляет весь выбор разом;
- радио внутри карточки меняет только свою позицию и переводит подсветку на «Ваш выбор»;
- состояние — `Record<category, cardId>` в `app/page.tsx`, ничего в URL и ничего в localStorage:
  демо обязано открываться одинаково с любого устройства;
- `app/embed/page.tsx` — только строка текущего набора, без радио: виджет узкий.

Вёрстка — существующие классы Tailwind из `app/page.tsx`, никаких новых зависимостей.

## 6. Проверка

`tests/combo.test.ts`, фикстуры строятся реальным вызовом `match` (ключ не нужен — объяснения
в смете не участвуют):

| Тест | Что проверяет |
|---|---|
| Эконом ≤ ваш выбор ≤ люкс | базовый инвариант порядка |
| Сумма = Σ цен + Σ проезда | арифметика, включая набор с `FLY_IN` |
| Пара 1 150 000 ₸ (HK-23752 / HK-31819) | тай-брейк по `id` детерминирован |
| Три прогона подряд идентичны | то же правило, что у `tests/core.test.ts` |
| Позиция без `cards` | категория в `missing`, строка её называет |
| Все позиции без `cards` | `hypothetical: true`, кратность к бюджету |
| Профиль в двух позициях | цена считается один раз, `alsoCovers` проставлен |
| Бюджет не назван | `deltaKzt === undefined`, `fitsBudget === true`, строка без хвоста |

Плюс `data/combo-scenarios.json` и эталон `samples/golden/C1.json` отдельным блоком в
`scripts/verify.ts`. Блок добавляется **после** существующего цикла по `scenarios.json`
и пишет в свои файлы — S1..S12 не пересчитываются.

## 7. Чего в этой версии нет — и почему

| Не делаем | Почему |
|---|---|
| Снять позиционный потолок по бюджету, оставить ограничение только на набор | Это правильнее по существу — сэкономленное на фотографе переехало бы ведущему — но меняет воронку и все эталоны. Решение принято: до защиты ядро не трогаем |
| Динамика по бюджету (рюкзак) | При сохранённом потолке ограничение не связывает: любой набор из прошедших карточек уже в бюджете. Код без применения |
| Собирать эконом из всего пула, а не из трёх показанных | Смета обязана ссылаться на то, что человек видит на экране. Расширение возможно: `match` уже знает пул, нужно лишь отдать его в ответе |
| Сохранение и отправка сметы | Ни базы, ни почты в проекте нет, за три часа не появится |
| Четвёртый набор «оптимум по score в бюджете» | Три варианта читаются за секунду, четыре — уже таблица. Селектор добавляется десятью строками, если после защиты попросят |

## 8. Ловушка демо

Бюджет для показа нужно брать реалистичный. Медианы по Алматы — фотограф 300 000, ведущий
1 000 000, лайв-бэнд 1 150 000, в сумме 2 450 000 ₸. При запросе «три позиции за 1 000 000 ₸»
не проходит **никто ни в одной позиции**, и единственное, что покажет смета — гипотетический
набор из §3.6.

Это не баг и показывать это не стыдно — наоборот, §3.6 ровно для такого случая и написан.
Но сценарий по умолчанию в `data/combo-scenarios.json` должен быть на 3 000 000 ₸, где видно
все три набора, а запрос на 1 000 000 ₸ стоит держать вторым сценарием — как демонстрацию того,
что сервис отвечает числом даже там, где отвечать нечем.
