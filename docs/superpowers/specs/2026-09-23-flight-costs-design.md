# Спека: стоимость перелёта в правиле FLY_IN

> 23.09.2026. Дополняет `docs/spec.md` (раздел 9, правило «Перелёт»).
> Цель: заменить дисклеймер «перелёт считается отдельной строкой» на конкретное число
> из реальных цен Aviasales — так, чтобы ядро осталось детерминированным,
> а демо не зависело от сети и от чужого API-ключа.

---

## 1. Что не так сейчас

`lib/relax.ts`, функция `flyIn()` предлагает подрядчика из другого города и пишет в карточку:

> «перелёт и проживание считаются отдельной строкой сметы и в цену не входят.
> Для коллектива расходы умножаются на состав.»

Это честно, но бесполезно: клиент не может принять решение, не зная порядка суммы.
Правило при этом сравнивает бюджет с **голым гонораром** — то есть формально предлагает
лайв-бэнд за 1 150 000 ₸ клиенту с бюджетом 1 200 000 ₸, хотя пять билетов туда-обратно
съедают остаток втрое.

Второе расхождение: `docs/spec.md` считает, что порог проходят **6 ведущих и 4 лайв-бэнда**,
но код отсекает только `venueCategories`. Три декоратора с чеком ≥ 1 млн проходят в код,
хотя по смыслу правила исключены — декоратор везёт материалы, а не себя.

---

## 2. Ограничение, которое упрощает всё

В каталоге **два реальных города**: Алматы (50 профилей) и Астана (15).
Третье значение `city` — «Зарубежье» (1 профиль), и `flyIn()` его уже исключает.

Значит вся задача — **один маршрут в две стороны: ALA ↔ NQZ**, на окне дат
`2026-09-23 … 2026-12-31` (100 дней). Не матрица городов, не геокодинг, не поиск аэропортов.

| Город | IATA |
|---|---|
| Алматы | `ALA` |
| Астана | `NQZ` |

> `NQZ`, не `TSE` — код Астаны сменился в 2020 году, старый отдаёт пустоту.

---

## 3. Решение: снимок в репозитории + скрипт обновления

Живой вызов API на каждый запрос отвергнут по трём причинам:

1. Ядро подбора — чистые функции без сети и без случайности (`docs/spec.md`, раздел 11).
   Сетевой вызов внутри `flyIn()` ломает это свойство.
2. Демо на площадке не должно зависеть от вайфая.
3. Жюри должно уметь воспроизвести прогон без регистрации в чужой партнёрке.
   Воспроизводимость и README — 25 баллов, столько же, сколько вся техреализация.

Берём тот же приём, которым в проекте уже сделаны эмбеддинги: **посчитано один раз,
лежит в репозитории, обновляется отдельным скриптом.**

## 4. `data/flights.json`

```jsonc
{
  "snapshotAt": "2026-09-23T09:00:00Z",
  "source": "travelpayouts /v2/prices/month-matrix",
  "currency": "KZT",
  "routes": {
    "ALA-NQZ": { "2026-09-25": 24900, "2026-09-26": 31200 },
    "NQZ-ALA": { "2026-09-25": 26400 }
  },
  "monthMedian": {
    "ALA-NQZ": { "2026-09": 28000, "2026-10": 27500, "2026-11": 29000, "2026-12": 34000 },
    "NQZ-ALA": { "2026-09": 29000, "2026-10": 28000, "2026-11": 30000, "2026-12": 35000 }
  }
}
```

`monthMedian` — не украшение. У Aviasales цена есть не на каждый день;
без запасного числа воронка провалится в дырку ровно на том запросе, который введёт судья.

---

## 5. `scripts/refresh-flights.ts`

4 месяца × 2 направления = **8 запросов**. Лимиты не задеваются.

```
GET https://api.travelpayouts.com/v2/prices/month-matrix
    ?origin=ALA&destination=NQZ&month=2026-10&currency=kzt
Header: X-Access-Token: <TRAVELPAYOUTS_TOKEN>
```

Из ответа берём минимальный `value` на каждый `depart_date`, медиану считаем по месяцу.
Запуск: `npm run refresh:flights`.

Поведение при сбое: **нет токена или сеть недоступна → скрипт печатает причину,
возвращает код 1 и не трогает существующий `flights.json`.** Снимок никогда не портится
частичной записью: файл пишется целиком после того, как собраны все 8 ответов.

`TRAVELPAYOUTS_TOKEN` идёт в `.env.example` с комментарием, что он нужен **только**
для обновления снимка, а не для запуска приложения.

## 6. `lib/travel.ts`

```ts
export type TravelCost = {
  perPersonKzt: number;   // туда + обратно на одного
  headcount: number;
  totalKzt: number;       // perPersonKzt * headcount
  basis: 'exact' | 'nearby' | 'median';
  basisNote: string;      // текст для карточки
  snapshotAt: string;
};

export function estimateTravelCost(
  fromCity: string,
  toCity: string,
  date: string,
  category: string,
): TravelCost | undefined;
```

Чистая функция: читает импортированный JSON, в сеть не ходит. Лестница запасных вариантов:

| basis | Когда | Что в карточке |
|---|---|---|
| `exact` | цена есть ровно на эту дату | «минимальная цена на 25 октября» |
| `nearby` | ближайшая дата в пределах ±3 дней | «на 25 октября цены нет, взята ближайшая — 27 октября» |
| `median` | в пределах ±3 дней ничего | «на эту дату цены нет, взята медиана октября» |

Обратный билет считается по дате мероприятия же — одним днём.
Проживание не считается вовсе, об этом карточка говорит прямо.

**Состав** — таблица на две строки, потому что поля в датасете нет:

| Категория | Состав | Обоснование |
|---|---|---|
| Ведущий | 1 | один человек |
| Лайв-бэнд | 5 | типовой состав: вокал, гитара, бас, клавиши, барабаны |

Других мобильных категорий среди проходящих порог нет. Число `5` — наше допущение,
и оно **проговаривается в карточке словами**, а не прячется в коде.

## 7. Изменения в `lib/relax.ts`

**7.1. Декоратор исключается.** Рядом с проверкой `isVenue(req.category)` добавляется
явный список `flyInExcluded = ['Декоратор', 'Флорист', 'Подарки и сувениры']` —
те же категории, что живут в `softDateCategories`: их продукт едет грузом, а не в кресле.
Список кладётся в `meta.json`, чтобы правило читалось из данных, а не из константы в коде.

**7.2. Бюджет не ужесточается, перелёт показывается числом.**
`FLY_IN` — правило из блока «ещё может подойти, если…». Его контракт (`docs/spec.md`, раздел 9):
карточка обязана сказать, какое условие ослаблено и **на сколько числом**. Поэтому
кандидат по-прежнему проходит по голому гонорару, но карточка называет полную сумму
и превышение:

> Гонорар 1 150 000 ₸ + перелёт 292 000 ₸ = **1 442 000 ₸**, это на 242 000 ₸ больше вашего бюджета.

Так блок не пустеет, а клиент видит правду. Жёсткий отсев `гонорар + перелёт ≤ бюджет`
здесь был бы ошибкой: он превратил бы послабление в обычный фильтр и убрал бы из выдачи
ровно те карточки, ради которых правило написано.

**7.3. Отсечка шума.** Кандидат не показывается, если `гонорар + перелёт > бюджет × 1.5`.
Порог вынесен в константу `FLY_IN_MAX_OVERRUN = 1.5` рядом с `FLY_IN_MIN_FEE`.
Если бюджет не назван, отсечка не применяется.

**7.4. Сортировка.** Внутри правила кандидаты сортируются по **полной стоимости**
(гонорар + перелёт), а не по гонорару. Тай-брейк по `id` сохраняется.

## 8. Что видит пользователь

> ✈️ **Перелёт Алматы → Астана и обратно: ≈ 292 000 ₸**
> 58 400 ₸ на человека × 5 (типовой состав лайв-бэнда — наше допущение, уточните у подрядчика).
> Минимальная цена Aviasales на 25 октября, снимок от 23.09.2026. **Проживание не посчитано.**

Три вещи сказаны честно: это минимум, а не гарантия; это снимок с датой;
ночёвка за рамками. При `basis: 'median'` первая строка получает приписку про медиану.

## 9. Тесты

`tsx --test`, без сети:

1. `estimateTravelCost` на дату, которая есть в снимке → `basis: 'exact'`, сумма = (туда + обратно) × состав.
2. Дата на 2 дня в стороне от имеющейся → `basis: 'nearby'`.
3. Дата, вокруг которой на ±3 дня пусто → `basis: 'median'`.
4. Лайв-бэнд даёт ровно впятеро больше, чем ведущий, на той же дате.
5. Запрос категории «Декоратор» из другого города не даёт ни одной карточки `FLY_IN`.
6. Кандидат с `гонорар + перелёт > бюджет × 1.5` не попадает в выдачу.
7. Снимок не содержит дат вне окна `META.dateWindow`.
8. Регресс: запрос «Ведущий, Астана, корпоратив» без бюджета даёт столько же карточек `FLY_IN`,
   сколько давал до изменений — отсечка по бюджету не должна срабатывать там, где бюджета нет.

## 10. README

Раздел «Перелёты» на три абзаца:

- **Откуда цифры** — Travelpayouts / Aviasales Data API, `month-matrix`, минимальные цены,
  найденные пользователями за последние 48 часов, дата снимка в файле.
- **Как обновить** — `npm run refresh:flights`, нужен `TRAVELPAYOUTS_TOKEN`.
- **Почему снимок, а не живой API** — детерминизм ядра, независимость демо от сети,
  воспроизводимость прогона без чужого ключа. Здесь же прямо сказано:
  **в полноценной реализации это живой вызов API с кэшем на несколько часов;
  врезка одна — тело `estimateTravelCost()`, интерфейс функции не меняется.
  В рамках хакатона на это сознательно не пошли из-за ограничения по времени.**

Отдельной строкой: Amadeus Self-Service выключен 17.07.2026, ключи деактивированы —
поэтому выбран Travelpayouts, а не «стандартный» Amadeus из туториалов.

## 11. Чего в этой работе нет (осознанно)

| Не делаем | Почему |
|---|---|
| Стоимость проживания | Второй источник данных. Карточка честно говорит, что ночёвка не посчитана |
| Другие маршруты | В каталоге два города. Формат `routes` расширяется добавлением ключа, код не трогается |
| Живой вызов API в рантайме | Ломает детерминизм ядра и привязывает демо к сети |
| Вебхуки на изменение цены | Их не существует ни у одного из провайдеров. Модель везде pull + кэш |
| Виджеты Travelpayouts в карточке | Это iframe: цену из него нельзя прочитать кодом, в фильтр он не годится |

---

## 12. Риск

Токен Travelpayouts выдаётся после регистрации в партнёрке Aviasales, и модерация может
не успеть до конца хакатона. Митигация: `data/flights.json` коммитится с первым же
успешным прогоном; если токена не будет вовсе — файл заполняется ценами, снятыми вручную
с aviasales.kz, а поле `source` честно говорит `manual`. Код, тесты, карточка и README
от этого не меняются.
