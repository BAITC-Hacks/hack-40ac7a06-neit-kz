# Спека: стоимость перелёта в правиле FLY_IN

> 23.09.2026, версия 2 (после трёх ревью). Дополняет `docs/spec.md` (раздел 9, правило «Перелёт»).
> Цель: заменить дисклеймер «перелёт считается отдельной строкой» на конкретное число
> из цен Aviasales — так, чтобы ядро осталось детерминированным, демо не зависело от сети,
> а каждое допущение было названо вслух.

---

## 1. Что не так сейчас

`lib/relax.ts:104-116`, функция `flyIn()` предлагает подрядчика из другого города и пишет в карточку:

> «перелёт и проживание считаются отдельной строкой сметы и в цену не входят.
> Для коллектива расходы умножаются на состав.»

Это честно, но бесполезно: клиент не может принять решение, не зная порядка суммы.
Правило при этом сравнивает бюджет с **голым гонораром** (`lib/relax.ts:36,100` — `passesBase`
вызывается без `skipBudget`), то есть формально предлагает лайв-бэнд за 1 150 000 ₸ клиенту
с бюджетом 1 200 000 ₸, хотя пять билетов туда-обратно превышают остаток бюджета **в 5,8 раза**.

Попутно вскрыты два расхождения кода с `docs/spec.md` §9:

| `docs/spec.md` §9 говорит | Код делает | Решение |
|---|---|---|
| «бюджет ≥ цена × 1.2» | множителя нет, просто `цена ≤ бюджет` | множитель отменяется явно: он был грубым запасом на перелёт, который теперь считается числом. Строка `docs/spec.md:253` правится в той же ветке |
| «порог проходят 6 ведущих и 4 лайв-бэнда» | отсекаются только `venueCategories`, поэтому проходят ещё 3 декоратора | декоратор исключается (§7.1) |

## 2. Ограничение, которое упрощает всё

В каталоге **два реальных города**: Алматы (50 профилей) и Астана (15).
Третье значение `city` — «Зарубежье» (1 профиль), и `flyIn()` его уже исключает.

Значит вся задача — **один маршрут в две стороны: ALA ↔ NQZ**, на окне дат
`2026-09-23 … 2026-12-31` (100 дней). Не матрица городов, не геокодинг, не поиск аэропортов.

| Город | IATA |
|---|---|
| Алматы | `ALA` |
| Астана | `NQZ` |

> `NQZ`, не `TSE` — код Астаны сменён решением IATA 06.04.2020, в силу с 08.06.2020,
> и обратно не вернулся после переименования города в 2022. Автокомплит Travelpayouts
> на `TSE` не отдаёт ничего казахстанского.

Направление `NQZ→ALA` обслуживает **ровно один профиль** — HK-97041 (Ведущий, Астана, 1 000 000 ₸).
Половина снимка существует ради него. Это дёшево (те же 4 запроса) и стоит сказать вслух,
а не делать вид, что маршрут симметричный.

## 3. Решение: снимок в репозитории + скрипт обновления

Живой вызов API на каждый запрос отвергнут по трём причинам:

1. Ядро подбора — чистые функции без сети и без случайности (`docs/spec.md` §11).
   Сетевой вызов внутри `flyIn()` ломает это свойство.
2. Демо на площадке не должно зависеть от вайфая.
3. README обещает «проверить без нашего API-ключа — одна команда» (`README.md:6`).
   Вторая обязательная регистрация это обещание убивает.

Берём тот же приём, которым в проекте уже закоммичен `data/explanations-cache.json`:
**посчитано один раз, лежит в репозитории, обновляется отдельным скриптом.**

> Ревью поймало, что в первой версии спеки этот довод опирался на эмбеддинги.
> Эмбеддингов в проекте нет — `README.md:215` прямо говорит, что семантический поиск
> в эту версию не вошёл. Прецедент заменён на реальный.

## 4. `data/flights.json`

```jsonc
{
  "snapshotAt": "2026-09-23T09:00:00Z",
  "source": "travelpayouts /v2/prices/month-matrix",
  "currency": "KZT",
  "oneWay": true,
  "routes": {
    "ALA-NQZ": { "2026-09-25": 24900, "2026-09-26": 31200 },
    "NQZ-ALA": { "2026-09-25": 26400 }
  },
  "monthMedian": {
    "ALA-NQZ": { "2026-09": 29700, "2026-10": 29800, "2026-11": 28300, "2026-12": 26800 },
    "NQZ-ALA": { "2026-09": 29900, "2026-10": 29800, "2026-11": 28500, "2026-12": 27000 }
  }
}
```

`monthMedian` — не украшение. У Aviasales цена есть не на каждый день;
без запасного числа воронка провалится в дырку ровно на том запросе, который введёт судья.

**Медианы идут вниз к декабрю, и это не опечатка.** Новогодней надбавки на ALA–NQZ нет:
фактические средние по aviasales.kz на 23.09.2026 — сентябрь 29 700 / октябрь 29 800 /
ноябрь 28 300 / декабрь 26 800 ₸ за сегмент. Если токена не будет и файл придётся заполнять
руками (§12), **заполнять «по интуиции» нельзя** — интуиция здесь ошибается на четверть
именно в декабре, где по `docs/spec.md` §2.2 занято 75% каталога и правило нужно чаще всего.

Медиана сентября считается **по дням внутри `META.dateWindow`** — это 8 дней, а не весь месяц.

## 5. `scripts/refresh-flights.ts`

4 месяца × 2 направления = **8 запросов**. Лимит эндпоинта — 300 запросов в минуту, запас огромный.

```
GET https://api.travelpayouts.com/v2/prices/month-matrix
    ?origin=ALA
    &destination=NQZ
    &month=2026-10-01
    &currency=kzt
    &one_way=true
    &limit=31
    &market=kz
    &show_to_affiliates=false
Header: X-Access-Token: <TRAVELPAYOUTS_TOKEN>
```

Каждый параметр здесь стоит не для красоты — три из них ревью нашло как дефекты первой версии:

| Параметр | Почему явно |
|---|---|
| `limit=31` | **дефолт 30.** Без него в октябре и декабре молча теряется 31-е число — последний день окна и самая очевидная демо-дата новогоднего корпоратива |
| `one_way=true` | дефолт уже `true`, но у соседнего `/v2/prices/latest` дефолт **обратный**. Полагаться на дефолт — риск ошибиться ровно вдвое и молча |
| `show_to_affiliates=false` | дефолт `true` отдаёт только цены, найденные по **вашему** партнёрскому маркеру. У свежего хакатонского аккаунта трафика нет: токен будет, ответ 200 — а данных ноль |
| `month=2026-10-01` | документирован формат `YYYY-MM-DD`, а не `YYYY-MM` |
| `market=kz` | дефолт `ru`; для тенговых цен на казахстанском маршруте берём казахстанский кэш |
| `currency=kzt` | публичного списка валют у Data API нет. Проверяется первым прогоном; если не поддержан — берём `usd`, конвертируем по `yasen.aviasales.com/adaptors/currency.json`, и `source` это фиксирует |

Из ответа берём минимальный `value` на каждый `depart_date`, медиану считаем по дням окна.
Запуск: `npm run refresh:flights` (через `tsx --env-file=.env.local`, как уже сделан `build:golden`).

**Проверки, после которых скрипт падает, а не пишет мусор:**

- в ответе непустой `return_date` → значит вернулся round-trip, и складывать туда+обратно нельзя;
- валюта ответа не `KZT`;
- нет токена или сеть недоступна.

Во всех случаях — сообщение, код 1 и **существующий `flights.json` не трогается**.
Файл пишется целиком после того, как собраны все 8 ответов. Пропущенные дни скрипт печатает списком.

`TRAVELPAYOUTS_TOKEN` идёт в `.env.example` с комментарием, что он нужен **только**
для обновления снимка, а не для запуска приложения и не для `npm run verify`.

## 6. `lib/travel.ts`

```ts
export type TravelCost = {
  perPersonKzt: number;   // туда + обратно на одного
  headcount: number;
  totalKzt: number;
  basis: 'exact' | 'nearby' | 'median';
  basisNote: string;
  snapshotAt: string;
};

export function estimateTravelCost(
  fromCity: string,
  toCity: string,
  date: string,
  category: string,
): TravelCost | undefined;
```

Снимок импортируется как `import flights from '@/data/flights.json'` — так же, как
`lib/catalog.ts:1-2` тянет каталог. **Не через `fs.readFileSync`**: в проекте уже есть шрам
на эту тему (`lib/explain.ts:48-55`, запись кэша обёрнута в try/catch «на Vercel ФС только для чтения»).

Лестница запасных вариантов:

| basis | Когда | Что в карточке |
|---|---|---|
| `exact` | цена есть ровно на эту дату | «минимальная цена на 25 октября» |
| `nearby` | ближайшая дата в пределах ±3 дней | «на 25 октября цены нет, взята ближайшая — 27 октября» |
| `median` | в пределах ±3 дней ничего | «на эту дату цены нет, взята медиана октября» |

На краях окна соседей меньше шести (для 23.09 — три, для 24.09 — четыре), поэтому фолбэк
там быстрее уходит в `median`. Демо-сценарий S6 стоит на 2026-09-25, то есть внутри
обрезанной зоны. Это ожидаемое поведение, а не баг, и так и написано в README.

**Функция возвращает `undefined`, если:**

- маршрута нет в снимке (город «Зарубежье» — он доступен в выпадающем списке, `app/page.tsx:98`);
- категории нет в таблице состава (см. ниже);
- снимку больше 30 дней.

Во всех трёх случаях карточка возвращается к прежнему тексту «перелёт считается отдельной
строкой сметы» — то есть деградирует к сегодняшнему поведению, а не ломается.

**Состав** — таблица на две строки, потому что поля в датасете нет:

| Категория | Состав | Статус |
|---|---|---|
| Ведущий | 1 | допущение: ведущий за 2 млн нередко едет с диджеем или техником |
| Лайв-бэнд | 5 | допущение: вокал, гитара, бас, клавиши, барабаны |

Оба числа — **допущения, а не данные**, и оба проговариваются в карточке словами.
Категория вне таблицы даёт `undefined`, а не «×1»: молча посчитать танцевальный коллектив
как одного человека хуже, чем не считать вовсе.

## 7. Изменения в `lib/relax.ts`

**7.1. Декоратор исключается.** В `flyIn()` рядом с `isVenue(req.category)` добавляется
проверка `softDateWindow(req.category) > 0` (`lib/catalog.ts:31-33`). Новый ключ в `meta.json`
**не заводится**: «работа не привязана к присутствию на площадке» и «едет грузом, а не в кресле» —
одно и то же свойство, уже записанное в `META.softDateCategories`. Второй рукописный список
разъехался бы с первым при первой же правке данных.

Реально это отсекает **только декоратора**: у «Флориста» максимум 300 000 ₸, у «Подарков
и сувениров» — 150 000 ₸, порог в миллион они не проходят никогда.

**7.2. Бюджет не ужесточается, перелёт показывается числом.**
`FLY_IN` — правило из блока «ещё может подойти, если…». Его контракт (`docs/spec.md` §9):
карточка обязана сказать, какое условие ослаблено и **на сколько числом**. Поэтому кандидат
по-прежнему проходит по голому гонорару, но карточка называет полную сумму и превышение.

Жёсткий отсев `гонорар + перелёт ≤ бюджет` здесь был бы ошибкой: он превратил бы послабление
в обычный фильтр и убрал бы из выдачи ровно те карточки, ради которых правило написано.

**7.3 и 7.4 первой версии отменены.** Ревью доказало, что оба пункта на этом каталоге
не могут ничего изменить, и мы их не реализуем:

- **отсечка `гонорар + перелёт > бюджет × 1.5`** недостижима. `passesBase` уже требует
  `гонорар ≤ бюджет`, а `FLY_IN_MIN_FEE` требует `гонорар ≥ 1 млн`, значит бюджет ≥ 1 млн.
  Условие сводится к «перелёт > 500 000 ₸», тогда как максимум по снимку — 5 × 70 000 = 350 000 ₸.
  Прогон 965 комбинаций кандидатов и бюджетов при четырёх ценах билета: **не сработала ни разу.**
- **сортировка по полной стоимости** тождественна текущей. Категория — жёсткий фильтр, значит
  внутри блока у всех кандидатов одна категория, один состав, один город и одна дата, то есть
  **один и тот же перелёт**. `гонорар + const` даёт тот же порядок, что `гонорар`.

Обе константы были придуманы при написании спеки и не переживают проверки данными.
В README это фиксируется одной строкой — жюри ценит отменённое решение с расчётом больше,
чем нереализованный пункт.

**7.5. Порог `FLY_IN_MIN_FEE = 1 000 000` остаётся — и это осознанное ограничение.**
Порог был прокси для «чек потянет перелёт». Теперь перелёт считается явно, и прокси не нужен.
Но снижать его в этой работе мы не будем, и вот честная цена решения:

- в S6 есть **HK-25279, лайв-бэнд за 800 000 ₸, свободен 25.09, берёт корпоративы**.
  С перелётом это 1 060 000 ₸ против 1 410 000 ₸ у показываемых — система прячет самое
  дешёвое предложение;
- в Астане отсутствуют шесть мобильных категорий, а порог оставляет из них только Лайв-бэнд.

Снижение порога потребовало бы состава ещё для четырёх категорий, которых в датасете нет, —
то есть новых выдумок ровно там, где вся фича про их отсутствие. Ограничение называется
в README списком допущений, а не замалчивается.

## 8. Точки врезки: что правится в каждом файле

Правки только в `flyIn()` **недостаточно**. Полный список — чтобы реализатор не гадал:

| Файл | Что |
|---|---|

| `lib/relax.ts:22-27` | `RelaxHit` получает `travel?: TravelCost` |

| `lib/explain.ts:16` | `PROMPT_VERSION` → `'v2'` |
| `lib/explain.ts:67-93` | в `factSheet` добавляются **отдельные числовые поля**: `перелёт_на_человека`, `состав`, `перелёт_всего`, `итого_с_перелётом`, `превышение_бюджета`, `снимок_цен_от` |

| `data/scenarios.json` | сценарии S10 и S11 |
| `data/meta.json` | не трогается (см. §7.1) |

**Валидатор объяснений пройдёт.** `numbersGrounded` (`lib/explain.ts:139-142`) сверяет числа
текста с `JSON.stringify(factSheet)`, вырезая пробелы с обеих сторон, а `factSheet` уже содержит
`послабление: card.relaxation?.detail` (`lib/explain.ts:91`). Сумма из `detail` совпадёт.
Отдельные числовые поля нужны для другого: чтобы модель не **выводила** проценты и округления,
которых в фактах нет.

**Шаблонная ветка сейчас про послабления не знает вообще.** При выключенном тумблере
«объяснения моделью» (`app/page.tsx:140`) — а это отдельно разрекламированный в README
демо-путь — текст скажет «остаётся 1 350 000 ₸ от бюджета» и ни слова о перелёте.

**Чип «остаток бюджета» будет спорить с плашкой.** `app/page.tsx:239-241` рисует
`budgetLeftover` из `lib/scoring.ts:160`, посчитанный как `бюджет − гонорар`. Рядом с
«перелёт 260 000 ₸, это на 210 000 ₸ больше вашего бюджета» это ровно та несогласованность,
которую §1 ставит в вину текущему коду.

## 9. Кэш и эталоны

Это блокер, а не гигиена. `samples/golden/S6.json` — единственный эталон с `FLY_IN`, и в нём
закоммичены объяснения модели:

> «Гонорар 1 150 000 ₸ **не включает перелёт и проживание**, которые считаются отдельной статьёй расходов.»

Как только рядом появится плашка с суммой, карточка будет одновременно называть число
и утверждать, что его не считают. Хуже: `cacheKey` (`lib/explain.ts:57-65`) считается по
`{req, cards:[{id, facts, diffs, price}], PROMPT_VERSION, MODEL}` и поля `relaxation` **не включает**,
хотя `relaxation.detail` уходит в промпт. Значит `npm run verify` покажет **PASS** на старом тексте.

Обязательная последовательность:

1. `PROMPT_VERSION = 'v2'` — инвалидирует кэш разом, без правки хеш-функции.
2. `Facts.travel` — после этого ключ кэша начинает зависеть от снимка цен структурно.
3. `npm run build:golden` **с живым `OPENAI_API_KEY`**, коммит нового
   `data/explanations-cache.json` и `samples/golden/*.json`.

Без шага 3 `--update` запишет шаблонные тексты, и обещание README «9/9 PASS без ключа»
формально сохранится, а фактически поменяет смысл.

## 10. Что видит пользователь

> ✈️ **Перелёт Алматы → Астана и обратно: от 260 000 ₸**
> 52 000 ₸ на человека × 5 — типовой состав лайв-бэнда, наше допущение, уточните у подрядчика.
> Минимальный тариф без багажа; инструменты оплачиваются отдельно.
> Снимок цен Aviasales от 23.09.2026, цена дня мероприятия.
> **Это нижняя граница:** вечернее мероприятие почти всегда означает ночёвку и обратный вылет
> на следующий день — ни проживание, ни другую цену обратного билета мы не считали.
> Ночной поезд Алматы — Астана дешевле в 2–3 раза.

Что здесь сделано осознанно:

- **«от», а не «≈».** Число построено из двух минимумов дня — это пол, а не оценка.
- **Про поезд сказано первыми.** Алматы — Астана это 1200 км, ночной Тальго и автобус
  существуют, поля о способе проезда в датасете нет. Молчать об этом — выдумывать тот самый
  факт, который весь проект обещает не выдумывать.
- **Противоречие «обратно тем же днём» ↔ «проживание не посчитано» снято текстом**,
  а не вторым источником данных: обратный билет взят по цене дня мероприятия **как нижняя
  оценка**, и сказано, что в реальности будет дороже.
- **Багаж назван.** Для лайв-бэнда минимальный тариф — худший из возможных: барабаны и клавиши
  удваивают сумму. Фича ради честности не должна занижать именно там, где показывается.

При `basis: 'median'` первая строка получает приписку про медиану. При `undefined` плашки нет,
остаётся сегодняшний текст.

## 11. Проверка

**Юнит-тесты** — новый файл `lib/travel.test.ts`, скрипт `"test": "tsx --test lib/travel.test.ts"`.
Тестового слоя в проекте сейчас нет вовсе (в `package.json` только `verify`, `demo`, `build:golden`),
так что это новая инфраструктура — но ровно один файл и одна строка, а не полдня.

1. Дата есть в снимке → `basis: 'exact'`, сумма = (туда + обратно) × состав.
2. Дата в двух днях от имеющейся → `basis: 'nearby'`.
3. Вокруг даты ±3 дня пусто → `basis: 'median'`.
4. Лайв-бэнд даёт ровно впятеро больше ведущего на той же дате.
5. Категория вне таблицы состава → `undefined`.
6. Город «Зарубежье» → `undefined`.
7. Снимок старше 30 дней → `undefined`.
8. В `routes` нет дат вне `META.dateWindow` (про `monthMedian` условие не применяется).

**Сценарии** — два новых в `data/scenarios.json`, потому что **ни один из девяти существующих
изменение не покажет**:

| Сценарий | Зачем |
|---|---|
| `S10`: Астана · Лайв-бэнд · корпоратив · 2026-09-25 · бюджет **1 200 000 ₸** | S6 идёт с бюджетом 2 500 000 ₸ — перелёт туда влезает, и флагманская фраза про превышение не появится никогда |

S11 заодно ловит побочный эффект, который легко пропустить: `collectRelaxations`
(`lib/relax.ts:181-190`) наливает слоты по `RULE_ORDER` по два на правило. Если FLY_IN

## 12. README

Раздела на три абзаца не хватит: воспроизводимость — 25 баллов, столько же, сколько вся
техреализация. Нужно семь пунктов:

   48 часов» относится к другим эндпоинтам — `/v2/prices/latest` и `/v3/prices_for_dates`).

3. **`npm run verify` и `npm run dev` работают без `TRAVELPAYOUTS_TOKEN`** — рядом с уже
   имеющимся обещанием `README.md:6`, иначе судья решит, что появилась вторая обязательная регистрация.
4. **Предупреждение:** `refresh:flights` меняет снимок, после него эталоны надо пересобрать.
   Для проверки проекта он не нужен и запускать его не надо.
5. **Список допущений одним местом** — состав 1 и 5; проезд считаем самолётом, поезд дешевле;
   проживание не посчитано; минимальный тариф без багажа; проезд считаем не входящим в гонорар,
   хотя поля об этом в анкетах нет; порог в 1 млн оставлен и прячет бэнд за 800 000 ₸.
6. **Строка в таблицу «пункт DoD → чем закрыт → где посмотреть»** — весь README построен на ней.
7. **Правки уже написанного:** `README.md:207` «Внешние сервисы: OpenAI API. Других интеграций
   нет» становится ложью; блок «Данные и интеграции» дополняется.

Отдельным абзацем — **почему снимок, а не живой API**, и прямо:

## 13. Чего в этой работе нет (осознанно)

| Не делаем | Почему |
|---|---|
| Стоимость проживания | Второй источник данных. Карточка честно говорит, что ночёвка не посчитана и что число — нижняя граница |
| Поезд и автобус | Нет источника по расписанию и ценам. Карточка называет самолёт верхней оценкой и говорит, что поезд дешевле |
| Снижение порога в 1 млн | Потребует состава ещё для четырёх категорий, которых в данных нет (§7.5) |
| Отсечка по перелёту и сортировка по полной стоимости | Доказано, что на этом каталоге не срабатывают (§7.3–7.4) |
| Другие маршруты | В каталоге два города. Формат `routes` расширяется ключом, код не трогается |
| Живой вызов API в рантайме | Ломает детерминизм ядра и привязывает демо к сети |
| Вебхуки на изменение цены | Их не существует ни у одного провайдера. Модель везде pull + кэш |
| Виджеты Travelpayouts в карточке | Это iframe: цену из него нельзя прочитать кодом, в фильтр он не годится |

## 14. Объём и порядок работ

Честно: **3–4 часа** с токеном, из них полчаса — перегенерация кэша и эталонов с живым
ключом OpenAI. Порядок такой, что после любого шага репозиторий рабочий:

1. `data/flights.json` — вручную с aviasales.kz, `source: "manual"` (10 мин).
2. `lib/travel.ts` + `lib/travel.test.ts` (40 мин).
3. Врезка по таблице §8 (40 мин).
4. `PROMPT_VERSION = 'v2'`, S10 и S11, `npm run build:golden` с ключом, коммит кэша
   и эталонов (30 мин).
5. README по семи пунктам §12 (30 мин).
6. `scripts/refresh-flights.ts` и `npm run refresh:flights` (40 мин).
7. Правка `docs/spec.md` §9 — строка «Перелёт» (10 мин).

**Шаг 6 — последний намеренно.** Он единственный зависит от чужого токена, и если времени
не хватит, README получает абзац «снимок снят вручную, вот источник» вместо «вот команда».
Для жюри разница невелика: в руках у него одинаковый JSON с указанным источником.
Всё остальное к этому моменту уже работает.
