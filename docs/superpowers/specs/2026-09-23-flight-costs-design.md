# Спека: стоимость перелёта в карточках из другого города

> 23.09.2026, версия 3 (после двух кругов ревью). Дополняет `docs/spec.md` §9.
> Привязка к коду — коммит `65bfa5c`. Ссылки даны **именами функций**, а не номерами строк:
> репозиторий правится параллельно, номера протухают за час.

---

## 0. Одно решение, которое определяет всё остальное

**Сумма перелёта живёт в `Card.relaxation.travel` и не попадает в `Facts`.**

`cacheKey` (`lib/explain.ts`) считается по `{req, cards:[{id, facts, diffs, price}], PROMPT_VERSION, MODEL}` —
поля `relaxation` в нём **нет**. Поэтому:

| Следствие | Значение |
|---|---|
| Ключ кэша объяснений не меняется | закоммиченный `data/explanations-cache.json` продолжает работать |
| `PROMPT_VERSION` не трогаем | перегенерация эталонов **не требует живого `OPENAI_API_KEY`** |
| Модель про перелёт не пишет — пишет плашка в интерфейсе | это и есть заявленный принцип «решает код, модель только формулирует» |
| Валидатор пересечения объяснений не задет | иначе одинаковая фраза о перелёте в двух карточках подняла бы jaccard с нынешних 0.350 выше порога 0.35 и обе карточки свалились бы в шаблон |

Проверено: объяснения в `samples/golden/S6.json` звучат «Гонорар 1 150 000 ₸, **перелёт и проживание
оплачиваются отдельно**». Плашка с числом этому не противоречит, а договаривает.

Работа при этом сокращается примерно с четырёх часов до полутора.

## 1. Что не так сейчас

`flyIn()` в `lib/relax.ts` предлагает подрядчика из другого города и пишет: «перелёт и проживание
считаются отдельной строкой сметы и в цену не входят». Честно, но клиент не может решать,
не зная порядка суммы.

Хуже — **несопоставимые цифры в одной выдаче**. Прогон S6 (Астана · Лайв-бэнд · корпоратив ·
2026-09-25 · бюджет 2 500 000 ₸) даёт сегодня:

| Блок | Карточка | Цена |
|---|---|---|
| `softCards` | HK-23752, Алматы, FLY_IN | 1 150 000 ₸ |
| `softCards` | HK-31819, Алматы, FLY_IN | 1 150 000 ₸ |
| `nearestCards` | HK-25279, Алматы, NEAREST | **800 000 ₸** |

Все трое — из Алматы, все летят одним и тем же рейсом. Если плашку вешать по признаку
`rule === 'FLY_IN'`, третья карточка останется без неё, и клиент решит, что дешёвый бэнд —
местный. Поэтому **перелёт считается по признаку `card.city !== req.city`**, а не по правилу.

Попутно закрываются два расхождения кода с `docs/spec.md` §9:

| `docs/spec.md` §9 | Код | Решение |
|---|---|---|
| «бюджет ≥ цена × 1.2» | множителя нет | отменяется явно: он был грубым запасом на перелёт, который теперь считается числом |
| «проходят 6 ведущих и 4 лайв-бэнда» | проходят ещё 3 декоратора | декоратор исключается (§7.1) |

## 2. Ограничение, которое упрощает всё

Два реальных города: Алматы (50 профилей) и Астана (15). Третье значение `city` — «Зарубежье»
(1 профиль), `flyIn()` его исключает. Значит вся задача — **один маршрут в две стороны, ALA ↔ NQZ**,
на окне `2026-09-23 … 2026-12-31` (100 дней).

| Город | IATA |
|---|---|
| Алматы | `ALA` |
| Астана | `NQZ` |

> `NQZ`, не `TSE`: код сменён решением IATA 06.04.2020, в силу с 08.06.2020, обратно не вернулся.
> Автокомплит Travelpayouts на `TSE` не отдаёт ничего казахстанского.

Оба направления нужны **в каждом случае**: подрядчик из Алматы летит в Астану и обратно.
Как *вылет* направление `NQZ→ALA` обслуживает ровно один профиль — HK-97041 (Ведущий, Астана,
1 000 000 ₸); как *обратное плечо* оно работает всегда.

## 4. `data/flights.json`

```jsonc
{
  "snapshotAt": "2026-09-23T09:00:00Z",
  "source": "travelpayouts /v2/prices/month-matrix",
  "currency": "KZT",
  "oneWay": true,
  "routes": {
    "ALA-NQZ": { "2026-09-25": 24900, "2026-09-26": 31200 },
    "NQZ-ALA": { "2026-09-25": 26400, "2026-09-26": 28100 }
  },
  "monthMedian": {
    "ALA-NQZ": { "2026-09": 29700, "2026-10": 29800, "2026-11": 28300, "2026-12": 26800 },
    "NQZ-ALA": { "2026-09": 29900, "2026-10": 29800, "2026-11": 28500, "2026-12": 27000 }
  }
}
```

`monthMedian` — не украшение: у Aviasales цена есть не на каждый день, и без запасного числа
воронка провалится в дырку ровно на том запросе, который введёт судья.

**Медианы идут вниз к декабрю, и это не опечатка.** Новогодней надбавки на ALA–NQZ нет.
Числа выше — медианы минимальных цен по дням месяца (не средние). Разница сентябрь → декабрь
около 10%, то есть интуитивная «новогодняя наценка» имеет неверный знак. Если токена не будет
и файл придётся заполнять руками (§14), **заполнять по интуиции нельзя**.

Медиана сентября считается по дням внутри `META.dateWindow` — это 8 дней, а не весь месяц.

### Канонические числа

Все примеры в этом документе выводятся отсюда и больше нигде не придумываются:

| Величина | Расчёт | Значение |
|---|---|---|
| Сегмент ALA→NQZ, 25.09 | из снимка | 24 900 ₸ |
| Сегмент NQZ→ALA, 25.09 | из снимка | 26 400 ₸ |
| **На человека туда-обратно** | 24 900 + 26 400 | **51 300 ₸** |
| **Лайв-бэнд (×5)** | 51 300 × 5 | **256 500 ₸** |
| Ведущий (×1) | | 51 300 ₸ |

## 5. `scripts/refresh-flights.ts`

4 месяца × 2 направления = 8 запросов. Лимит эндпоинта — 300 запросов в минуту.

```
GET https://api.travelpayouts.com/v2/prices/month-matrix
    ?origin=ALA&destination=NQZ&month=2026-10-01&currency=kzt
    &one_way=true&limit=31&market=kz&show_to_affiliates=false
Header: X-Access-Token: <TRAVELPAYOUTS_TOKEN>
```

Каждый параметр стоит не для красоты:

| Параметр | Почему явно |
|---|---|
| `limit=31` | **дефолт 30**, справка прямо велит ставить 31 для длинных месяцев. Без него в октябре и декабре молча теряется 31-е — последний день окна и очевидная дата новогоднего корпоратива |
| `one_way=true` | дефолт уже `true`, но ошибка здесь была бы ровно вдвое и молча, а параметр документирован только в Help Center и отсутствует в dev-доках |
| `show_to_affiliates=false` | дефолт `true` сужает выдачу до цен, найденных с партнёрским маркером. Ставим `false`, чтобы не зависеть от этого |
| `month=2026-10-01` | для этого параметра документирован формат `YYYY-MM-DD`, а не `YYYY-MM` |
| `market=kz` | по умолчанию рынок определяется по `origin`, а при неудаче берётся `ru`. Ставим явно, чтобы состав данных не зависел от определения. **На валюту не влияет** — это разные параметры |
| `currency=kzt` | публичного списка валют нет; `kzt` присутствует в `yasen.aviasales.com/adaptors/currency.json`. Проверяется первым прогоном, иначе `usd` + конвертация, и `source` это фиксирует |

Обработка ответа:

1. Берём минимальный `value` на каждый `depart_date`.
2. **Отбрасываем дни вне `META.dateWindow`** — запрос за сентябрь вернёт и 01–22.09.
3. Медианы считаем по оставшимся дням.

**Проверки, после которых скрипт падает, а не пишет мусор:** непустой `return_date`
(приходит пустой строкой `""`, поэтому проверка — `if (r.return_date)`); валюта ответа не KZT;
нет токена или сети. Во всех случаях — сообщение, код 1, **существующий файл не трогается**.
Файл пишется целиком после сбора всех 8 ответов; пропущенные дни печатаются списком.

`TRAVELPAYOUTS_TOKEN` идёт в `.env.example` с пометкой, что он нужен **только** для обновления
снимка — не для `npm run dev` и не для `npm run verify`.

## 6. `lib/travel.ts`

```ts
export type TravelCost = {
  perPersonKzt: number;   // туда + обратно
  headcount: number;
  totalKzt: number;
  basis: 'exact' | 'nearby' | 'median';
  basisNote: string;
  snapshotAt: string;
};

export function estimateTravelCost(
  fromCity: string, toCity: string, date: string, category: string,
): TravelCost | undefined;
```

Снимок импортируется как `import flights from '@/data/flights.json'` — как `lib/catalog.ts`
тянет каталог, **не через `fs.readFileSync`**: в проекте уже есть шрам на эту тему
(запись кэша в `lib/explain.ts` обёрнута в try/catch «на Vercel ФС только для чтения»).

Лестница по каждому плечу отдельно: `exact` → ближайшая дата в пределах ±3 дней (`nearby`) →
медиана месяца (`median`). **У плеч может быть разный исход — в `basis` попадает худший**
(`median` хуже `nearby` хуже `exact`). На краях окна соседей меньше шести, поэтому там
фолбэк быстрее уходит в `median`; демо-дата 2026-09-25 лежит в этой зоне. Это ожидаемо, а не баг.

**Функция возвращает `undefined`, если:**

- нет маршрута для пары городов — в частности когда **`req.city === 'Зарубежье'`** (город есть
  в `META.cities` и в выпадающем списке интерфейса);
- категории нет в таблице состава.

**Проверки возраста снимка в функции нет.** Она была в версии 2 и вырезана: это единственное
место, где ядро читало бы системные часы. Последствие было бы календарным — `npm run verify`
начал бы падать сам собой через месяц, без единой правки кода, и обещание README «9/9 PASS
без ключа» стало бы ложным по календарю. Возраст снимка — строка в карточке и в README,
а не ветка в коде; протухание при желании проверяет CI или сам скрипт обновления.

**Состав** — таблица на две строки, потому что поля в датасете нет:

| Категория | Состав | Статус |
|---|---|---|
| Ведущий | 1 | допущение: считаем, что едет один |
| Лайв-бэнд | 5 | допущение: вокал, гитара, бас, клавиши, барабаны |

Оба числа — допущения, а не данные, и оба названы в карточке словами. Категория вне таблицы
даёт `undefined`, а не «×1»: молча посчитать танцевальный коллектив как одного человека
хуже, чем не считать вовсе.

## 7. Изменения в правилах

**7.1. Декоратор исключается из FLY_IN.** В `flyIn()` рядом с `isVenue(req.category)` добавляется
`softDateWindow(req.category) > 0`. Новый ключ в `meta.json` не заводится: «работа не привязана
к присутствию» и «едет грузом, а не в кресле» — одно свойство, уже записанное
в `META.softDateCategories`. Реально отсекает **только декоратора**: у Флориста максимум 300 000 ₸,
у Подарков 150 000 ₸, порог в миллион они не проходят.

**Честно о последствии:** карточка декоратора с экрана **не исчезает**. Прогон
«Астана · Декоратор · свадьба · 2026-10-05» показывает: сейчас два декоратора идут как FLY_IN;
после правки `softCards` пустеет, и `nearestCandidates()` возвращает **всех трёх** в блок
«ближайшее, что есть в каталоге». Правило перестаёт утверждать, что декоратор прилетит, —
но подрядчик остаётся виден как честное «ближе этого в каталоге нет».

> Версия 2 утверждала, что освободившиеся слоты достанутся BUDGET_STRETCH и DURATION_STRETCH.
> Это невозможно по построению: оба зовут `passesBase` без `skipCity`, а FLY_IN срабатывает
> ровно тогда, когда категории в городе нет. Слоты уходят в `nearestCards`.

**7.2. Бюджет не ужесточается, перелёт показывается числом.** FLY_IN — правило из блока
«ещё может подойти, если…». Его контракт (`docs/spec.md` §9): карточка обязана сказать,
какое условие ослаблено и **на сколько числом**. Кандидат проходит по голому гонорару,
карточка называет полную сумму и превышение. Жёсткий отсев `гонорар + перелёт ≤ бюджет`
превратил бы послабление в обычный фильтр и убрал бы из выдачи ровно те карточки,
ради которых правило написано.

**7.3. Отсечка и пересортировка из версии 2 отменены.** Ревью доказало, что оба пункта
на этом каталоге не могут ничего изменить:

- **отсечка `гонорар + перелёт > бюджет × 1.5`** недостижима: `passesBase` требует
  `гонорар ≤ бюджет`, `FLY_IN_MIN_FEE` требует `гонорар ≥ 1 млн`, значит бюджет ≥ 1 млн,
  и условие сводится к «перелёт > 500 000 ₸» — вдвое выше максимума по снимку;
- **сортировка по полной стоимости** тождественна текущей: категория — жёсткий фильтр,
  значит внутри блока у всех кандидатов одна категория, один состав, один город и одна дата,
  то есть один и тот же перелёт. `гонорар + const` даёт тот же порядок, что `гонорар`.

Обе константы были придуманы при написании спеки и не пережили проверки данными.
В README это фиксируется строкой: отменённое решение с расчётом ценнее нереализованного пункта.

**7.4. Порог `FLY_IN_MIN_FEE = 1 000 000` остаётся.** Он был прокси для «чек потянет перелёт»,
и после появления настоящего числа прокси не нужен, — но снижение потребовало бы состава
ещё для четырёх категорий, которых в датасете нет. Цена решения: в Астане отсутствуют шесть
мобильных категорий, а порог оставляет из них только Лайв-бэнд (Декоратор уходит отдельным
решением §7.1). Ограничение называется в README списком допущений.

> Версия 2 утверждала здесь, что порог «прячет самое дешёвое предложение» — бэнд HK-25279
> за 800 000 ₸. **Это было неверно:** он на экране, в `nearestCards` (см. §1). После правки
> §8 он получит ту же плашку перелёта, что и остальные, и окажется честно самым дешёвым:
> 1 056 500 ₸ против 1 406 500 ₸. Ложное самообвинение убрано.

## 8. Точки врезки

Правки только в `flyIn()` недостаточно. Полный список — по именам символов, а не по строкам:

| Файл | Символ | Что |
|---|---|---|
| `lib/travel.ts` | — | новый модуль, `estimateTravelCost` |
| `data/flights.json` | — | новый файл (§4) |
| `lib/types.ts` | `Card.relaxation` | добавляется `travel?: TravelCost`. Union правил дублирует `RelaxRule` из `lib/relax.ts` — правятся оба места |
| `lib/relax.ts` | `RelaxHit` | добавляется `travel?: TravelCost` |
| `lib/relax.ts` | `flyIn()` | §7.1 — исключение декоратора; текст `detail` больше не говорит «проживание», это ушло в плашку |
| `lib/match.ts` | `softRanked`, `nearestRanked` | **оба** места, где навешивается `relaxation`, получают `travel`. Условие — `card.city !== req.city`, **не** `rule === 'FLY_IN'` |
| `app/page.tsx` | `CardView`, блок `relaxation` | плашка перелёта под `label`/`detail` |
| `app/page.tsx` | чип «остаток бюджета» | подпись становится «остаток без перелёта», когда у карточки есть `travel` |
| `scripts/verify.ts` | `snapshotCard` | добавляются `travel?.totalKzt` и `relaxation?.detail` — иначе текст плашки не закреплён ничем и его поломка пройдёт как PASS |
| `package.json` | scripts | `test`, `refresh:flights` |
| `.env.example` | — | `TRAVELPAYOUTS_TOKEN` |
| `data/scenarios.json` | — | S11 и S12 (§11) |
| `docs/spec.md` | §9, строка «Перелёт» | переписывается: множителя ×1.2 нет, декоратор исключён, перелёт считается числом |
| `lib/explain.ts` | — | **не трогается** (см. §0) |
| `lib/scoring.ts` | — | **не трогается**: `buildFacts` не знает правила, протаскивать его пришлось бы через три вызова, а при отрицательном остатке чип просто исчезает. Вместо этого правится подпись чипа |
| `data/meta.json` | — | **не трогается** (см. §7.1) |

**Отдельная находка, которую стоит закрыть заодно:** `cacheKey` не включает `relaxation`,
хотя `relaxation.detail` уходит в промпт через `factSheet`. Сегодня это нам на руку (§0),
но при следующей правке текста любого послабления кэш молча отдаст старое объяснение.
Одна строка — `relaxation: c.relaxation` в `cards.map(...)`. `undefined` выбрасывается
`JSON.stringify`, поэтому сценарии без послаблений ключ не меняют. **Делать это нужно
отдельным коммитом после текущей работы**, иначе перегенерация эталонов потребует ключа OpenAI.

Три строки вместо шести из версии 2: шесть строк оговорок на одно число читаются не как
честность, а как неуверенность команды в собственной цифре. Здесь не потеряно ничего:

- **«от», а не «≈»** — число построено из двух минимумов дня, это пол;
- **поезд назван** — Алматы—Астана это 1200 км, ночной Тальго существует, поля о способе
  проезда в датасете нет, и молчать об этом значило бы выдумать ровно тот факт, который
  весь проект обещает не выдумывать;
- **багаж назван** — для лайв-бэнда минимальный тариф худший из возможных: барабаны и клавиши
  легко удваивают сумму;
- **противоречие «обратно тем же днём» ↔ «проживание не посчитано» снято текстом**, а не
  вторым источником данных: слова «по факту выйдет дороже» покрывают и ночёвку, и другую
  цену обратного билета.

При `basis: 'median'` первая строка получает приписку про медиану. При `undefined` плашки нет —
остаётся сегодняшний текст послабления.

Числа в этом блоке — из §4, и в коде они берутся из снимка. **В промпт модели они не идут**
(§0), поэтому валидатор `numbersGrounded` их не увидит и забраковать не может.

## 11. README

Воспроизводимость — 25 баллов, столько же, сколько вся техреализация. Раздела на три абзаца
не хватит; и **начинать надо не с перелётов**:

**Сначала — починить то, что README врёт уже сейчас, без участия этой фичи:**

- «сверяет **9** сценариев; 9/9 PASS» — сценариев десять, после этой работы будет двенадцать;
- блок «Ожидаемый вывод» печатает «карточек 3+0», тогда как `verify` уже выводит три числа
  и знает про `nearestCards`;
- «Внешние сервисы: OpenAI API. Других интеграций нет» — становится ложью.

**Потом — про перелёты:**

1. **Откуда цифры** — Travelpayouts / Aviasales Data API, `month-matrix`, самые дешёвые цены
   по дням из поискового кэша Aviasales. Кэш Data API хранится 7 суток (это общее свойство API,
   а не особенность этого эндпоинта); справка рекомендует кэшировать результат у себя на сутки —
   мы кэшируем в репозитории.
2. **Как обновить** — `npm run refresh:flights`, нужен `TRAVELPAYOUTS_TOKEN`.
3. **`npm run verify` и `npm run dev` работают без `TRAVELPAYOUTS_TOKEN`** — рядом с уже
   имеющимся обещанием «проверить без нашего ключа», иначе судья решит, что появилась
   вторая обязательная регистрация.
4. **Предупреждение:** `refresh:flights` меняет снимок, после него эталоны надо пересобрать.
   Для проверки проекта он не нужен.
5. **Список допущений одним местом** — состав 1 и 5; считаем самолёт, поезд дешевле;
   проживание не посчитано; тариф минимальный, без багажа; считаем, что проезд не входит
   в гонорар, хотя поля об этом в анкетах нет; порог в 1 млн оставлен.
6. **Честно про статус фичи:** стоимость проезда **не закрывает ни один пункт DoD** — это работа
   сверх требований кейса. Придумывать под неё строку в таблицу DoD задним числом не будем.
7. **Почему снимок, а не живой API** — и прямо: **в полноценной реализации это живой вызов
   с кэшем на несколько часов; врезка одна — тело `estimateTravelCost()`, интерфейс функции
   не меняется. В рамках хакатона на это сознательно не пошли из-за ограничения по времени.**

Строкой: Amadeus Self-Service выключен 17.07.2026, ключи деактивированы, хост песочницы
`test.api.amadeus.com` не резолвится — поэтому Travelpayouts, а не «стандартный» Amadeus
из туториалов. Ссылка на источник кладётся в `docs/` рядом со скриншотом Aviasales.

## 12. Чего в этой работе нет (осознанно)

| Не делаем | Почему |
|---|---|
| Стоимость проживания | Второй источник данных. Карточка говорит, что по факту выйдет дороже |
| Поезд и автобус | Нет источника по расписанию и ценам. Карточка называет авиацену и говорит, что поездом дешевле; наша цифра — нижняя граница **авиаварианта**, а не всех способов проезда |
| Снижение порога в 1 млн | Потребует состава ещё для четырёх категорий, которых в данных нет (§7.4) |
| Отсечка по перелёту и пересортировка | Доказано, что на этом каталоге не срабатывают (§7.3) |
| `travel` в `Facts` и в промпте | Ломает кэш, требует ключа OpenAI и упирается в валидатор пересечения (§0) |
| Другие маршруты | Формат `routes` расширяется ключом, код не трогается |
| Живой вызов API в рантайме | Ломает детерминизм ядра и привязывает демо к сети |
| Вебхуки на изменение цены | Их не существует ни у одного провайдера. Модель везде pull + кэш |
| Виджеты Travelpayouts | Это iframe: цену из него нельзя прочитать кодом, в фильтр он не годится |

## 13. Объём и порядок

**1,5–2 часа** без скрипта, **2,5–3 часа** со скриптом. Порядок такой, что после любого шага
репозиторий рабочий:

| # | Шаг | ~ |
|---|---|---|
| 1 | `data/flights.json` вручную с aviasales.kz, `source: "manual"` | 20 мин |
| 2 | `lib/travel.ts` + `lib/travel.test.ts` | 30 мин |
| 3 | Врезка по таблице §8: типы, `flyIn`, оба места в `match.ts`, плашка и чип в `app/page.tsx` | 30 мин |
| 4 | S11, S12, `snapshotCard`, `npm run verify -- --update` (**без ключа OpenAI**) | 20 мин |
| 5 | README: сперва починить «9 сценариев» и ожидаемый вывод, потом семь пунктов §11 | 30 мин |
| 6 | `docs/spec.md` §9, строка «Перелёт» | 10 мин |
| 7 | `scripts/refresh-flights.ts` и `npm run refresh:flights` | 40 мин |

**Шаг 7 последний намеренно** — он единственный зависит от чужого токена. Если времени
не хватит, README получает абзац «снимок снят вручную, вот источник и скриншот» вместо
«вот команда»: у жюри в руках одинаковый JSON с указанным источником.

**Объём ручного заполнения на шаге 1 ограничен явно:** даты обоих демо-сценариев (25.09, 05.10)
плюс первая неделя окна плюс четыре медианы на месяц. Остальные дни сознательно уходят
в `median` — иначе шаг 1 растягивается на час и тратится на дни, которых никто не введёт.
