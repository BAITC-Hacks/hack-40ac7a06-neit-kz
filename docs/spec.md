# Спека v2: умный подбор подрядчиков (#79-lite)

> Версия 2, 23.09.2026. Основана на ТЗ кейса (`ТЗ-kejs-79-lite.md`), разборе `dataset.csv` (66 профилей)
> и решениях команды. Все числа ниже посчитаны на данных и перепроверены.
> Цель документа — чтобы любой из команды мог объяснить жюри, что происходит внутри пайплайна.

---

## 1. Что строим

Заказчик описывает мероприятие **своими словами** в мини-чате. Система понимает запрос, при необходимости
задаёт уточняющий вопрос, показывает подтверждение «правильно ли я понял», а затем возвращает
**до 3 карточек подрядчиков с объяснением, почему именно они** — плюс честный разбор, кого и почему не хватило.

Приоритет жюри: **качество объяснений > честная обработка редких, занятых и пустых > скорость > интерфейс.**
Баллы: работоспособность 25 · техреализация 25 · **README и воспроизводимость 25** · ценность 15 · потенциал 10.

**Главный принцип:** решения принимает детерминированное ядро. Модель работает только на двух языковых
краях — понять запрос на входе и объяснить результат на выходе. Всё, что она сказала, проверяется кодом.

## 2. Что данные говорят о задаче

### 2.1 «Меньше трёх» — это норма, а не край

Прогон 816 комбинаций (город × категория × формат × 4 даты):

| Исход | Доля |
|---|---|
| Ноль свободных | 39% |
| 1–2 кандидата | 30% |
| Такой категории в городе нет | 24% |
| **Три и больше** | **7%** |

**Вывод, определяющий продукт:** в 93% запросов «вот вам три карточки» не существует. Поэтому воронка отсева
и ответ «почему меньше и что можно поменять» — главный экран, а не сноска.

### 2.2 Ловушки данных (все проверены)

| Факт | Следствие |
|---|---|
| `max_hours` пуст ровно у 3 категорий: Флорист, Декоратор, Подарки и сувениры (9 профилей) | Наивный фильтр длительности обнуляет три категории целиком. Пустой `max_hours` проходит **всегда** |
| Порядок в `languages` не нормализован: `русский\|казахский` — 9 профилей, `казахский\|русский` — тоже 9 | Парсить только в множество, никогда не сравнивать строкой. То же с `event_formats` |
| Ресторан, Отель, Загородная площадка — **подмножества** Банкетного зала; Нац. ансамбль **≡** Танцевальный коллектив (те же 4 id) | Два разных пресета вернут те же карточки. Нужен маркер «также числится как…» |
| У 25 профилей бренд в описании ≠ `anon_name` (HK-74147 «Джет Блэк» → в тексте «Инуяша и Кагоме») | Модели **запрещено** брать имя из описания |
| После анонимизации поехал род: HK-62242 «Юдзи… она вошла… Его география… работал в Японии» | Цитировать только фрагменты-факты, не предложения целиком |
| `price_imputed` у 18 профилей, включая **все** банкетные залы, рестораны, загородные площадки и отели | Вся ценовая вилка площадок — оценка составителей. В карточке нужна пометка «цена ориентировочная» |
| 13 синтетических профилей — сплошной блок id HK-90001…HK-90013, средняя длина описания 178 против 479 у реальных | Бейдж в карточке; своих профилей не добавляем |
| Занятость: октябрь–ноябрь 38–40%, **декабрь 75%**; 6 декабря занято 85% каталога, 12 октября — 23% | Успешные сценарии берём в октябре–ноябре, пустые — в декабре |
| Слова «розы» нет **ни в одном** описании. Шымкент не встречается ни в поле города, ни в текстах | Готовые тесты на «не выдумывать» |

### 2.3 Самый тяжёлый вход для DoD

Запрос «Национальный ансамбль · Алматы · той · 09.10» даёт ровно три кандидата: **HK-92824, HK-36965, HK-39301**.
У всех цена 500 000 ₸, `max_hours` 2, только казахский, тот же формат. Структурно неразличимы.
Отличаются только описаниями в 68–108 символов: «прославляем казахскую песню» / «ансамбль Sailor Dala» /
«впервые выступивший перед главой государства».

Если наши объяснения различают эту тройку — требование DoD «сотри имена, не перепутаешь» закрыто
на худшем возможном примере.

## 3. Архитектура: шесть слоёв

```
Чат пользователя
   ↓
L0  ПРИЁМ: извлечение параметров моделью → валидация кодом → уточняющий вопрос → подтверждение пользователем
   ↓ (структурированный запрос: жёсткие параметры + мягкие пожелания)
L1  ЖЁСТКИЕ ФИЛЬТРЫ: 7 шагов, каждый пишет в воронку сколько отсеял и почему
   ↓
L2  СКОРИНГ: детерминированные веса, тай-брейк по id
   ↓
L3  КОНТРАКТ ФАКТОВ: чем карточки отличаются ДРУГ ОТ ДРУГА, раздача различителей
   ↓
L4  ОБЪЯСНЕНИЯ: один вызов модели на все карточки → валидатор кодом → кэш
   ↓
L5  РЕЛАКСАЦИЯ: если карточек меньше трёх — отдельный блок «ещё может подойти, если…»
```

Слои L1–L3 и L5 полностью детерминированы и работают **без модели**. L0 и L4 — языковые, и оба обвязаны
проверками в коде.

## 4. L0. Приём запроса: мини-чат

### 4.1 Что делает

Пользователь пишет свободным текстом: «нужен ведущий на свадьбу в Алматы 18 ноября, бюджет до миллиона,
чтобы вёл на казахском и без пошлых конкурсов».

Модель со структурированным выводом (JSON Schema, `temperature = 0`) раскладывает это на:

- **жёсткие параметры** — город, дата, тип мероприятия, категория, бюджет, длительность, язык;
- **мягкие пожелания** — список коротких формулировок: «ведёт на казахском», «без пошлых конкурсов»;
- **`missing`** — чего не хватает для запуска поиска;
- **`unsupported`** — то, чего нет в каталоге, с точной цитатой пользователя.

### 4.2 Правило «не выдумывать» — обеспечивается кодом, а не просьбой в промпте

Каждое извлечённое значение проходит валидацию:

| Параметр | Правило валидации |
|---|---|
| Город | Только из списка каталога через словарь синонимов. «Шымкент» → `unsupported`, а не подстановка ближайшего |
| Категория | Только из 17 категорий через словарь синонимов («тамада», «ведущий» → Ведущий) |
| Формат | Только из 6 форматов |
| Дата | Парсится кодом, не моделью. Обязана попадать в окно 23.09–31.12.2026, иначе — вопрос пользователю |
| Бюджет | Число обязано присутствовать в тексте пользователя. «Недорого» — это не бюджет, это `missing` |
| Язык, длительность | Из перечислений; отсутствуют — остаются пустыми, **умолчаний не подставляем** |

Ничего не додумываем: если пользователь не назвал бюджет, мы его **спрашиваем**, а не берём медиану.

### 4.3 Уточнение

Обязательный минимум для поиска: **город, дата, категория, бюджет**. Формат — желателен.

Если чего-то не хватает — **один вопрос за раз, максимум два круга**, затем показываем форму и просим
дозаполнить руками. Бесконечного диалога нет: это инструмент подбора, а не собеседник.

### 4.4 Подтверждение — обязательный шаг

Перед поиском пользователь видит сводку и подтверждает:

> **Правильно понял?**
> Ведущий · Алматы · свадьба · 18 ноября 2026 · до 1 000 000 ₸
> Пожелания: ведёт на казахском · без пошлых конкурсов
> [Искать] [Изменить]

Любое поле правится руками. Это одновременно UX-требование заказчика, страховка от ошибок разбора
и то, что делает систему детерминированной: **поиск запускается от подтверждённой структуры, а не от текста**.

### 4.5 Честный ответ на то, чего нет

- «Хочу ведущего из Шымкента» → «В каталоге только Алматы и Астана, Шымкента нет. Искать в Алматы или Астане?»
- «Флориста, который украсит розами» → пожелание принимается как мягкое, но ни в одном профиле роз не упомянуто,
  и в карточке будет честно: «про розы в профиле не сказано; указано: работают с сезонными и привозными цветами,
  собирают композиции под цветовую палитру». **Выдумывать розы запрещено.**

## 6. L1. Жёсткие фильтры

Фиксированный порядок, на каждом шаге пишем в воронку, сколько отсеялось и почему:

1. город → 2. категория → 3. формат → 4. свободен на дату → 5. бюджет → 6. язык (если категория языко-критичная) → 7. длительность.

Воронка возвращается в ответе API всегда и рисуется на экране: «город 50 → категория 10 → формат 9 → свободен 3 → бюджет 3».

Плюс **именные near-miss**: 2–3 подрядчика, отсеянных на последнем шаге, с причиной и числом —
«Буллма прошла город, категорию, формат, свободна; отсеяна бюджетом: 1 000 000 при вашем 700 000».

---

## 7. L2. Скоринг: веса и их обоснование

Считается **только среди прошедших жёсткие фильтры**. Всё, по чему кандидат прошёл фильтр, различающей
силы не имеет — город, формат и «свободен на дату» одинаковы у всех по построению. Поэтому веса отданы тому,
что различает кандидатов между собой.

| Фактор | Вес | Как считается | Почему столько |
|---|---|---|---|
| **Совпадение с пожеланиями** | **0.35** | Доля подтверждённых пожеланий: точное вхождение термина и синонимов + косинус эмбеддинга пожелания к предложениям описания | Это то, что пользователь сказал сам. Главный источник ценности и главный различитель |
| **Специализация под формат** | 0.15 | Чем уже набор форматов подрядчика, тем выше: тот, кто берёт только свадьбы, точнее под свадьбу, чем универсал на все шесть | Различает почти всегда: у ведущих Алматы от 2 до 4 форматов |
| **Запас по бюджету** | 0.15 | Нормированный остаток бюджета, вклад ограничен сверху | Ценность для клиента, но не должен выигрывать «просто самый дешёвый» |
| **Доказательства опыта** | 0.10 | Регулярки по описанию: годы опыта (16 профилей), число мероприятий (3), места в рейтингах и награды (4) | Единственный объективный сигнал качества в данных |
| **Язык** | 0.10 | Для языко-мягких категорий: совпадение + запас по числу языков | В критичных категориях язык уже отработал как фильтр |
| **Запас по длительности** | 0.10 | `max_hours − duration`, нормировано; `null` — нейтрально, без штрафа | Отличает «ровно впритык» от «с запасом» |
| **Близость описания к типу мероприятия** | 0.05 | Косинус эмбеддинга описания к запросу | Слабый сигнал: описания короткие, медиана 313 символов. Вес намеренно низкий |

**Если пожеланий нет** — вес 0.35 распределяется между остальными факторами пропорционально. Правило
фиксированное и задокументированное, случайности нет.

**Детерминизм:** score округляется до 4 знаков перед сравнением, тай-брейк — по `id`.

**Что НЕ влияет на ранг:** флаги `synthetic`, `price_imputed`, `city_imputed`. Они честно показываются
в карточке, но не наказывают подрядчика — иначе мы подменяем данные оценкой их качества.

## 8. L3–L4. Факты, различители и объяснения

### 8.1 Контракт фактов

До обращения к модели код считает для выжившей тройки оси различия: ранг цены и дельта к соседу,
запас часов, число и состав форматов, языки, плотность календаря, извлечённые факты из описания,
подтверждённые и неподтверждённые пожелания, флаги честности.

Затем каждой карточке **жадно раздаются 2 оси, значение которых уникально внутри тройки**, и двум карточкам
запрещено использовать одну ось с одинаковым значением. Различие существует в данных **до** генерации —
модель только переводит его в русский текст.

### 8.2 Объяснение

Один вызов на все карточки сразу, `temperature = 0`, на входе только факты. Порядок предложений в карточке:

1. **Различитель** — то, чего нет у других: «Единственный из троих держит площадку 10 часов».
2. **Улика из описания** — пересказ фрагмента, не дословная цитата.
3. **Цена как сравнение**: «1 000 000 — на 350 000 дороже соседа, в бюджет укладывается».
4. **Компромисс или «почему не выше»**: «Ниже первого: берёт 4 формата из 6, описание в основном про свадьбы».
5. **Честность, если применимо**: «цена в каталоге ориентировочная», «профиль синтетический»,
   «про розы в профиле не сказано».

Общие для всех факты (город, формат, свободен на дату) в текст объяснения **не попадают** — они уходят в чипсы.
Тогда текст физически не может стать взаимозаменяемым.

### 8.3 Валидатор объяснений — это код, а не промпт

1. Каждое число, дата и язык из текста обязаны присутствовать в фактах карточки — защита от выдумок.
2. В объяснении минимум два конкретных факта.
3. Попарное пересечение слов между объяснениями одного ответа ниже порога.
4. У каждого объяснения есть хотя бы один токен, которого нет в других — буквальная проверка DoD.
5. Блок-лист общих фраз: «отличный выбор», «идеально подойдёт», «профессионал своего дела», «индивидуальный подход».
6. Модели запрещено брать имя подрядчика из описания.

Брак → один повтор с указанием различителей → шаблонное объяснение из фактов.
**Пустого экрана у судьи не будет никогда**, даже если API недоступен.

## 9. L5. Релаксация: блок «ещё может подойти»

**Инвариант, который нельзя ломать:** основная тройка — только те, кто прошёл все жёсткие условия.
Альтернативы живут в отдельном массиве ответа и отдельном блоке на экране. Блок появляется,
**только если основных карточек меньше трёх**. Максимум 3 карточки, максимум 2 на одно правило.

Формулировка, защищающая от обвинения в подмене: **мы не двигаем дату мероприятия клиента —
мы двигаем дату работы подрядчика.**

| Правило | Кому применимо | Условие | Данные |
|---|---|---|---|
| **Мягкая дата** | Флорист (−1 день), Декоратор (−1, −2), Подарки и сувениры (−1…−3). Только назад | `max_hours = null` — признак из датасета, а не наше мнение | Спасает 52–80% пустых дней в этих категориях |
| **Формат-сосед** | той → свадьба (**только со знанием казахского**), конференция → корпоратив, день рождения → юбилей | Совместная встречаемость 100% / 100% / 83%. Обратные направления запрещены (40% / 39% / 25%) | Самый массовый эффект |
| **Перелёт** | Мобильные категории, чек от 1 млн, бюджет ≥ цена × 1.2. Площадки исключены, «Зарубежье» исключено | 6 ведущих и 4 лайв-бэнда проходят порог. Для коллектива честно пишем: перелёт умножается на состав | Единственное правило, спасающее «категории нет в городе» |
| **Бюджет** | +15%, если `price_imputed`; +10%, если цена заявлена подрядчиком. Выше — никогда | Цены всех площадок — оценочные | |
| **Длительность** | `max_hours ≥ duration − 2` с оговоркой «переработка обсуждается отдельно» | Ведущий на 10 часов: строго 4 из 15, мягко 10 из 15 | Если останется время |

Каждая мягкая карточка обязана содержать: какое условие ослаблено и **на сколько числом**, чем это оправдано
(поле данных или фрагмент описания), и что клиент должен проверить сам.

**Честная цифра для защиты:** послабления спасают 26–28% пустых выдач. Остальные 72–74% остаются честным нулём.

Плюс подсказка для гибкого клиента: «если сдвинуть мероприятие на 19 октября, свободных станет трое».

## 10. Четыре исхода

| Исход | Когда | Что видит пользователь |
|---|---|---|
| `MATCHED` | есть хотя бы один прошедший | карточки + воронка + блок альтернатив, если меньше трёх |
| `NO_CATEGORY_IN_CITY` | в городе нет такой категории | «В Астане в каталоге нет лайв-бэндов. Все 5 в Алматы, четверо свободны 25 сентября — можно обсудить переезд» |
| `NO_FORMAT_IN_POOL` | категория есть, но формат не берёт никто | «Оба ведущих церемонии в Алматы работают только со свадьбами и той. Для корпоратива нужен ведущий — их 10» |
| `NO_ONE_PASSES` | кандидаты были, все отсеялись | «9 ведущих берут корпоративы в Алматы, все девять заняты 12 декабря. Первого октября свободны трое» |

Четвёртый исход — находка из данных: таких пар «категория есть, формат не берёт никто» в датасете 47.
Без него они все падали бы в «все заняты», а это другой ответ пользователю.

## 11. Детерминизм и скорость

- L1, L2, L3, L5 — чистые функции, без обращения к модели и без случайности.
- Сортировка стабильная: округление score до 4 знаков + тай-брейк по `id`.
- `temperature = 0` **не гарантирует** детерминизм у провайдера — гарантию даёт **кэш** по хешу
  `запрос + список id + факты + версия промпта + модель`. Так и говорим жюри: честнее, чем заявлять ложную гарантию.
- Разбор чата тоже кэшируется по нормализованному тексту.
- Эмбеддинги 66 профилей считаются один раз и лежат в репозитории.
- Ориентир: холодный запрос 2–4 секунды, повторный — мгновенно. Требование ТЗ — до 10 секунд.

## 12. Экран

1. **Чат** — поле ввода, ответ системы, уточняющий вопрос, карточка подтверждения «правильно понял?» с правкой полей.
2. **Карточки** — имя, категория, город, цена, объяснение, чипсы фактов, бейджи «синтетический профиль» и
   «цена ориентировочная», маркер «также числится как Ресторан».
3. **Воронка «как мы отбирали»** с именными near-miss.
4. **Блок «ещё может подойти, если…»** — свёрнут по умолчанию, появляется только при нехватке карточек.
5. **Тумблер «стереть имена»** — превращает карточки в «Подрядчик A/B/C». Буквальная демонстрация DoD жюри.
6. **Тумблер «без модели»** — показывает шаблонные объяснения. Страховка и наглядная демонстрация слоистости.

Красоту не полируем: ТЗ прямо говорит выбирать объяснения, а не интерфейс.

## 14. Воспроизводимость

- **`npm run verify`** — прогоняет все сценарии и сверяет с эталонными ответами, печатает PASS/FAIL. **Ключ не нужен.**
- **Эталонные ответы** на каждый сценарий закоммичены в репозиторий.
- **Кэш объяснений и эмбеддинги** закоммичены: жюри получает настоящие тексты без нашего ключа.
- **Режим без ключа**: шаблонные объяснения из фактов, баннер в интерфейсе.
- **Тесты**: детерминизм (три прогона подряд идентичны), различимость объяснений, работа ядра без модели.
- **Единый файл сценариев** — из него читают и кнопки-пресеты, и скрипт проверки, и тесты. Расхождение README и демо исключено.
- В README — таблица «пункт DoD → чем закрыт → где посмотреть», в каждой строке ссылка на файл репозитория.

## 16. Риски и капканы

| Риск | Подстраховка |
|---|---|
| API недоступен, кончились кредиты | Кэш в репозитории + шаблонные объяснения + тумблер «без модели» |
| Vercel: файловая система только на чтение | Кэш читаем из репозитория, пишем в память, запись в `try/catch` |
| `new Date('2026-11-14')` парсится как UTC и уезжает на день | Даты сравнивать **строками**, `Date` в фильтре занятости не использовать |
| Эталонные ответы протухнут к проверке 24–28.09 | Нигде не сравнивать дату запроса с «сегодня» |
| После правки промпта кэш отдаёт старые тексты | Версия промпта и имя модели — в ключе кэша |
| Модель выдумала число или имя | Валидатор ловит и заменяет на шаблон |
| Чат разобрал запрос неверно | Обязательный шаг подтверждения + правка полей руками |
| Судья вводит бюджет наугад и получает пустоту | Подсказка реальной вилки цен по категории и городу + пресеты |
| Демо 6 декабря | Успешные сценарии — октябрь и ноябрь; 6 декабря занято 85% каталога |

## 17. Порядок работы

1. Каркас, данные из CSV в JSON, README-скелет.
2. **L1 + воронка + четыре исхода + L2 скоринг — без модели.** На этом этапе продукт уже демонстрируем.
3. L5 релаксация: мягкая дата, формат-сосед, перелёт, бюджет.
4. L3 контракт фактов + L4 объяснения с валидатором и кэшем.
5. L0 мини-чат: разбор, валидация, уточнение, подтверждение.
6. Пресеты, тумблеры, чипсы, бейджи.
7. `verify`, эталонные ответы, тесты.
8. README, скриншоты, прогон всех сценариев.

Если время кончается, режем в обратном порядке, но **пункты 1–4 неприкосновенны**: без них нет продукта.
Чат (пункт 5) ценен, но при нехватке времени вырождается в форму с полем «пожелания» — и это честно
описывается в разделе «Ограничения».
